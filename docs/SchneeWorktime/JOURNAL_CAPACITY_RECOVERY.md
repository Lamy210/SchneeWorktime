# Journal上限到達時のデータ保全と移行設計（BUG-01 / P0）

## 事実と対象

現行schema-1は全イベントを単一SQLite snapshot payloadに保存し、store revisionとevent数を一致させる。replayの上限は10,000件、SnapshotStoreのpayload上限は16MiB。残500件で警告、残100件以下では新規勤務・再開を拒否するが、残2件から必要な観測・退勤に限定する予約枠をPR #79で統合した。実際のディスク容量やpayload上限はイベント数から保証できない。

残1件で直接Store退勤を保存できる場合と、10,000件に達したactive勤務の退勤を拒否する場合をJournalCapacityTestsで検証する。後者は現行制約の再現であり、正常な退勤の受入完了ではない。Applicationでは退勤前にobserveが新規イベントを必要とする場合があるため、残1件を退勤可能と断定しない。

## 方針比較

| 案 | 利点 | 不採用条件・リスク |
|---|---|---|
| A: 上限だけ拡大 | 変更が小さい | 全履歴再生・payload上限・バックアップ上限に影響し根本解決しない |
| B: 退勤と必要観測の予約枠 | 短期的な枯渇リスク低減 | 観測回数・ディスク・失敗再試行は無限に保証できない。枯渇時の救済にはならない |
| C: schema-2の保存方式と明示移行 | 履歴・監査を保持した長期運用が可能 | 旧版互換、検証、復旧、性能、格納容量と世代管理の設計が必要 |

推奨: Bの安全な抑制を別途設計しつつ、根本対策はC。現PRは境界の回帰テストと設計のみ。数値の引き上げや削除、既存データの自動移行、新形式の実装は行わない。

## schema-2の受入条件（未承認・未実装）

- 全イベントおよび監査の保全を必須にし、単なる現在状態のsnapshot化だけで過去の証跡を破棄しない。
- 旧版の正常DBを読み取り専用で検証し、元DBのepoch/revision/完全bytes、reference context、観測世代、全勤務日、全監査、active IDを保存する。新形式へ移行した候補の再読込でDomain値を照合する。
- 現在の排他ロック・明示確認・新規保全パス・CASを維持する。旧DBへの上書き・初期化・自動採用は禁止。失敗時は元DBと保全コピーを維持する。新形式の採用と切戻しは専用の世代フェンスを設計する。
- active勤務を移行でき、退勤前に必要な未確認観測を保存できること。観測を省略して実働を確定しないこと。通知は確定状態だけから再収束する。
- バックアップと復旧の全データサイズ制限、未知イベント、複数writer、強制終了、ストレージ枯渇を検証する。旧版からの読み込み保証は別途定義する。
- 10,000件以上のfixture、CapturedReferenceを含む監査、未知timezone、active/onBreak、旧版のnil context、観測checkpointの復元、過去日訂正を含め、入出力完全照合・失敗時の非破壊・性能計測を行う。

## 現行版で上限に達した場合

新規記録の追加を繰り返さず、既存DBを初期化しない。アプリを終了し、[原本保全](RECOVERY_RUNBOOK.md#原本の保全)に従い保存フォルダ全体を保全する。読込可能な場合は別の所有者専用フォルダへJSONバックアップを保存する。バックアップは旧版へ戻せることや退勤を確定できることを保証しない。active勤務の安全な移行・終了は未実装であり、利用者の実績を推定して記録しない。リリース判定はNO-GOを維持する。

## Applicationでの容量枯渇・再起動の検証

`JournalReserveRecoveryTests` は旧版で作成された上限間近のactive journalと正確なcheckpointをテスト専用DBに構築する。予約枠を既存のreplayに適用しないことを前提とし、以下の3件を検証する。

| 残容量 | 操作 | 期待結果 |
|---|---|---|
| 2 | 20秒の未観測期間後に再起動し、次の秒に退勤 | 観測と退勤を各1件保存し、実働上下限と再起動後の履歴を維持 |
| 1 | 20秒の観測空白後に退勤、さらに再起動 | 必要な観測を拒否し、完了扱いにせず、journal・checkpointを不変に保つ |
| 0 | 未観測期間後に再起動 | 既存controllerの起動拒否、論理バックアップの検証はStoreから可能 |

残1/0件で新規観測が必要な場合、現行Applicationの通常起動は拒否される。起動失敗時のメニューには「起動できない記録の保全」UIがあり、セッションロックを保持できる場合、`PreservationBackup.write` / `CatalogBackup.writePreservationBackup` により読取専用JSONを別の所有者専用ディレクトリへ保存できる。今回、残0/1件でWorktimeControllerの起動が拒否された直後にも原本bytes・観測checkpointを変更せず保全可能で、既存出力を上書きしないことをApplication結合テストに追加した（最新CI・macOS実機は別途確認）。

このJSON保全は**退勤成功・容量枯渇からの通常起動復旧・元DBの物理的な保全・旧epoch再採用を保証しない**。セッションロック不足、破損・SQLite sidecar、権限・容量不足の場合は失敗し得る。起動失敗から実機UIでの復旧導線とschema-2の安全なライブ移行は依然P0。退勤を強制したり未観測時間を実働として採用する経路は追加しない。
