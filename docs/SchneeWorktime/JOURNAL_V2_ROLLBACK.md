# schema-2 Journalの限定ロールバック（初回リリース用内部API）

## 対象と前提

- 正常に読み書きできる**schema-2**ライブDBから、**同一epochの厳密に過去のJournal行prefix**へ戻す操作だけを扱う。
- 候補と現在の両方に未終了の勤務日がある場合は拒否する。別epoch・schema-1・不正なアーカイブ・分岐したJournalも拒否する。
- 破損DBの置換・別世代からの復旧・一般的なバックアップインポート・自動起動時復元・Controller連携は**対象外**。
- アーカイブは署名されていない。読み取れたこと自体は出所・真正性を証明しない。

## 2段階のフロー

1. 呼び出し側が原本の単一所有者ロックを保持し、最新のschema-2セッションをロードする。
2. `previewRollback(file:now:matching:)` で安全な私有ディレクトリのファイルを一度だけ読み取る。`from: Data` も利用できる。検証済みのイベントbytesをメモリ内候補に固定し、**プレビューで書込みを行わない**。
3. 利用者が削除される勤務日数とリビジョンを明示確認し、通知予約と書込みを停止する。現在DB**以外の**所有者専用ディレクトリに未使用の保全先を選ぶ。
4. `commitRollback(proposal,preserveCurrentAt:now:)` は現行epoch/revision・全Journal bytes・カタログ・Checkpointの一致を再検証。**現行世代の正規バックアップを排他書出し、fsync・再読込照合してから**ライブDBを変更する。
5. `BEGIN IMMEDIATE`の中で再度CAS/Journal prefix/勤務終了状態を検証し、Journal行の置換、Checkpoint削除、**新epoch**への更新を単一トランザクションで行う。
6. コミット後に再読込照合。失敗した場合は成功とも失敗とも断定せず`committedButUnverified`を返す。自動再試行は禁止。呼び出し側は既存Controller/通知/セッションを破棄し、新世代を再ロード・再構築する。

## 制約・障害モード

- schema-2に限り`JournalV2Backup.maxBytes=96MiB`で保存・読取・限定ロールバックのプレビューを実行する。既存の`BackupFile.maxBytes=24MiB`はschema-1とCSVで維持。96MiB超、原本を保全できない場合は復元を開始しない。最大容量での負荷・RAM・クラッシュ/ディスク障害評価は継続P0。
- プレビュー後の並列更新、Checkpointだけの更新、削除reset、ファイル差替えでCASが失敗すれば復元しない。
- 保全先に既存ファイル/シンボリックリンクがある場合は拒否する。DBディレクトリ配下は保全先に選べない。
- ディスク容量不足・SQLiteのCOMMIT曖昧結果・ファイルシステム障害で利用者が手動復旧する手順は、実機・障害注入の証跡を別途整備する。
- 旧epochへの自動復元を拒否するため、全履歴削除後の旧バックアップは自動復活しない。
- SQLiteの論理更新であり、SSDからの物理完全消去や外部エクスポート削除を保証しない。
- UI/通知停止/アプリ内バックアップ台帳の連携は未実装。**v1.0の公開はNO-GO**。

## 検証

`JournalV2RollbackTests`で、正常prefixからの復元・保全読戻し・新epoch・再起動後の整合性、既存保全先、古い確認案/異なるepoch、未終了勤務/同revision、意味的に妥当な分岐アーカイブ、`BEGIN IMMEDIATE`中の強制例外によるROLLBACK、DB内の保全先拒否を検証する。

24MiB超の専用I/O・復元プレビュー回帰試験を追加するが、最大64MiBの実履歴を使った実測、手動RC・macOS実機・電源障害は未検証。
