# schema-2 全履歴削除のデータ所在・世代境界（P0作業中）

対象: v1.0未リリースのschema-2 Journal。Issue #113、AC-74/134/135/158。
この資料は**ソースコードから確認した範囲の暫定インベントリ**であり、全データ消去の受入証跡ではない。

## AC-74/134/135/158に向けた消去設計・受入条件（未実装）

1. アプリが所有する専用ディレクトリと生成台帳を定義し、新しい管理ファイルは生成時から識別する。旧版由来の未登録ファイルは未確定として表示し、自動削除しない。外部exportは明示的に対象外。
2. 読取り専用の削除プレビューで対象、除外、不明、件数を区別する。台帳は相対パス・種類・生成世代・ファイルidentityに紐付ける。勤務区間や本文などの個人データを削除ログへ複製しない。
3. 所有ロックを保持し、書込み/通知/バックアップ作成を停止。削除前にDBの世代と管理台帳を照合し、永続化された削除intentを記録する。意図確認後に対象が変われば拒否する。
4. SQLite resetと管理ファイル削除は単一トランザクションにできない。永続intentを用い、DB reset前後・管理ファイル削除途中・完了記録直前の各中断状態を区別する。起動時は未完了intentの再検証を優先し、旧epochの書込みや復元を許さない。曖昧な場合は停止し、未知のファイルを消さない。
5. 管理ディレクトリへの処理は固定root・所有者/権限・リンク禁止・identity再照合を要求する。再帰的な任意パス削除、SQLite sidecarの直接削除、外部exportへのunlinkは禁止する。実装では既存の安全なファイルI/OとOS APIの適合性を確認する。
6. 成功は対象の消去と新epoch・空Journal・所有通知取消・管理台帳の整合性を確認した場合に限定する。単なるDB初期化や部分成功を「全履歴消去完了」と表示しない。物理完全消去、OS管理のコピーまでは保証しない。

追加検証: 同名の外部ファイル保持、未知ファイル保持、symlink/hardlink・パス差替え・権限不一致拒否、削除途中の強制終了、再起動時の冪等な再開、ディスク不足、旧epochの復元拒否、通知取消未収束。実機における全対象の一覧と削除後の再走査が必要。**本設計だけでは受入条件をpassedにしない。**

## 管理履歴インベントリの先行実装（CI未確認）

- 固定root `managed-history-v1` の直下に限定する新規管理名前空間を定義。管理対象は生成元が明示登録する `backup-<UUID>.json` / `diagnostic-<UUID>.json` とし、相対パスを任意入力から構築しない。既存外部export、旧復旧候補、移行候補は自動採用しない。
- 登録形式はschema番号、種別、UUID、生成epoch、device/inode/size/mtime/ctime。重複と件数・入力サイズの上限を検証する。登録データの真正性は将来の信頼済み生成・永続化処理の責務であり、JSONを読み込めること自体は所有権の証明ではない。
- 読取り専用インベントリは所有者専用親/管理ディレクトリ、リンク禁止、通常ファイル、単一hardlink、所有者と権限、identityの一致を確認。登録済み一致、欠落、変更、危険、未登録を区別し、未一致があれば新規消去計画を完成扱いにしない。読み取り中の親/管理ディレクトリのidentityも再検証する。
- このコードは**削除の許可・実行APIではない**。同一uidによる悪意ある操作や内容の完全一致を保証せず、将来の実行時には所有ロック・完全なDB CAS・対象再検証・永続intentが必要。登録台帳の永続化、生成処理、ファイル消去、中断復旧、起動時ゲート、実機の既存ファイル調査は未実装。

## 台帳初回永続化・消去intentの先行実装（CI未確認）

- `ManagedHistoryRegistryFile`: 専用アプリディレクトリの固定ファイル `managed-history-registry-v1.json` に初回台帳のみ公開。既存 `BackupFile` の非上書き・private権限・fsync・読戻しを利用する。欠落/破損/リンクは空台帳として扱わない。台帳の更新、信頼済み生成元からの登録、世代管理は後続。
- `ManagedHistoryErasureIntentFile`: 固定ファイル `managed-history-erasure-v1.json` へ1件のintentを永続化する。上書き禁止。保存前に台帳と管理インベントリを再照合し、異常があれば拒否。曖昧な公開結果を自動リトライしない。
- intentはソースepoch/revision、予定target epoch、管理台帳と管理rootのidentityを保持する。勤務区間や診断本文は保持しない。Store内部APIでは予定target epochを受け取るよう拡張した。UIからの実運用resetと消去再開は未接続。
- 復旧判定は次のとおり。判定そのものは消去権限を発行しない。旧世代のままなら再確認が必要であり、同revisionでもCheckpoint/全Journal CASの再確認は後続の実行器が担う。
  - ソース版かつ管理対象が一致: 再確認が必要。
  - 予定した新epoch、revision 0、空カタログ・Checkpointなし、管理対象が一致または欠落: 残ファイル一覧、または最終検証待ち。
  - 無関係の世代、台帳差異、rootの差替え、変更済み・危険・未登録ファイル: 停止。
- 新epochで欠落を検出しても消去完了とは断定しない。永続的なファイル単位の進捗、通知取消、DB/台帳の再検証が必要。完了時のintent/台帳更新、起動ゲート、実際の消去処理は未実装。
- 新規回帰試験4件（初回公開・上書き拒否、世代フェンス・欠落時の判定、未登録・root差替え、破損/リンク/欠落拒否）。試験用一時ディレクトリのみを操作する。実機、電源断・障害注入、AC-74/134の最終検証は未完了。

## 予定epochのreset接続と起動遮断（CI未確認）

- Store内部の `commitManagedReset` は完全なJournal/Checkpoint CAS付きreset previewとintentのソース版を検証し、intentを非上書きで永続化した後、台帳・管理root・保存済みintentを再照合する。SQLiteトランザクション内で再度完全CASを行い、intentに記録済みのtarget epochへ切り替える。現epochと同じtargetは拒否。
- 旧世代のまま中断したintentを自動再試行しない。通常のDB限定resetでも未完了intentがあれば別のepochへ切り替える操作を拒否する。保存済みintentは成功・失敗を問わず保持する。
- `DesktopStorageLaunchGuard` は固定intentパスの存在を先に確認する。壊れた内容やdangling symlinkも遮断対象。DBが未作成でも初期化を許さない。I/Oエラーは安全側に停止する。これは通常の起動/セッション開始ゲートであり、任意の同一uidプロセスを阻止するOS強制機構ではない。
- このStore内部APIはまだUIから呼ばれない。管理台帳更新・信頼済み生成元、明示的な全消去確認、通知停止、ファイル単位の進捗/消去・完了処理、専用復旧画面は後続。遮断解除の自動化はない。外部ファイルや既存ユーザーデータの削除は実行しない。
- 回帰試験5件を追加：予定epochと再読込、同revisionのCheckpoint競合、永続化後の再試行拒否、破損intentによる既存/新規起動遮断、dangling symlink拒否。合成データのみ。電源断の実機試験とAC-74/134完了証跡は未実施。

## アプリケーション層の安全な論理削除（PR #127）

1. 呼出し側は`LocalSessionLock`等の単一所有者排他を保持し、書込み/通知予約を止める。**通知取消の収束はこのコアの責任外**。
2. `JournalV2WorktimeController.previewReset(sample:)`はOS時計と現在のJournal全行/Checkpoint CASを検証して日数・監査数・active状態を返す。**プレビュー中のDB変更はしない**。
3. 利用者が削除範囲と旧世代の再利用不可を明示確認してから`commitReset`。プレビュー後の同revisionでのCheckpoint変更も拒否する。
4. SQLite `BEGIN IMMEDIATE`内で元Journal全行・catalog・Checkpoint一致を再検証し、イベント/Checkpoint削除と新epoch採番をアトミックに確定する。
5. 成功した場合、アプリケーション層セッションは新epochと空カタログに更新。失敗、書込み結果不確実、クラッシュ時は**既存セッションの継続利用/自動リトライを禁止**し、正常なDBから再ロードして世代を確認する。
6. 同じepochからの厳密な旧Journal prefixのみを許す限定ロールバックは、reset後の旧epochアーカイブを拒否する。旧バックアップを自動採用しない。

## 現在のDB内の論理削除UI（実装・CI未確認）

- 書込みセッションと所有者ロックが存在する場合のみ、勤務日数・訂正数・未終了勤務の有無・revisionをプレビューする。残容量不足でも削除確認は可能。
- 完全な確認コンテキスト（セッション、epoch/revision、Checkpoint）を固定し、文字列「削除」の完全一致を要求する。正常なCheckpoint更新も旧確認を失効させる。勤務中は再確認が必要になる場合がある。
- 確定後は保守状態で打刻・観測・通知再予約を止め、所有通知の取消収束と保存状態を再確認する。既存resetの完全CAS・原子的epoch切替を使い、成功/失敗を問わず書込みセッションを破棄して既存DBを読み取り専用で再読込する。
- このUIの名称と案内は「現在のDB内の勤務記録を削除」に限定する。ユーザー管理ファイル、設定、未確定の管理対象ファイル、物理的な残留データは消去しない。AC-74/134等の完全な受入条件は未達。
- 新規回帰試験3件は明示同意、正常観測による確認失効、外部Checkpoint競合を対象とする。CIと実機確認は別途。

## 限定ロールバックの安全なアプリケーション層フロー

- `previewRollback(file:sample:)`は読み取り専用。旧epoch・分岐履歴・active勤務・未来/不正な候補を拒否する。
- 利用者が復元対象と失われる履歴を明示確認し、呼出し側が通知を止め、既存のない所有者専用ディレクトリの保存先を選ぶ。
- `commitRollback`は**現在の正常世代全体を保全して読戻し照合したあと**SQLiteのCAS/新epochで復元する。保存失敗または競合なら置換しない。ファイルが公開された後の同期/読戻し失敗など曖昧な状態は安全側で停止し、自動再試行しない。
