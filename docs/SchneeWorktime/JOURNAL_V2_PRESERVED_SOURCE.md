# Journal v2: 現行schema-1ファイルからの保全読込と隔離候補作成

`JournalStagingDatabase.createFromPreservedSource(at:in:now:)` は既存の
`SnapshotStore.readForPreservation(at:)` を使い、稼働DBをREADONLY・副作用なしで読み込んでから、
新しい隔離先ディレクトリのschema-2候補を作成する。

## 事前条件
- 呼び出し元が専用のセッションロックを取得し、**元DBへの並列書込みを排除**する。
- 既存schema-1のSQLite通常ファイルと保護されたディレクトリを使う。候補DBやリンクは元DBとして認めない。
- 元データのJournal/Domain検証が失敗した場合、候補は作成しない。
- 作成後に元DBを再読込してsnapshotのepoch・revision・payload全体一致を確認する。差分検知時はエラーとし、途中生成候補は調査用に残す。

## 未実装・非保証
- これは**候補作成のみ**で、採用・移行・復旧・自動切替を行わない。
- 再読込後の競合は防止できない。実際の採用には**原子的CAS・世代フェンス・バックアップ・ロールバック**が必須。
- 同一UIDのプロセスによるディレクトリ差替え、ACL、電源断、容量枯渇は別途検証。
- 新しいファイルパスを本番DBとして直接利用しない。旧アプリのダウングレードは保証しない。

## 回帰テスト
正常schema-1からの候補作成と原本bytes不変、元DB欠落時の候補未生成、
schema-2候補をschema-1元DBとして誤入力したときの拒否。

v1.0への自動移行を許可する変更ではない。
